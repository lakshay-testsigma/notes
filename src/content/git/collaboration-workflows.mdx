One shared notebook everyone scribbles in, versus everyone drafting on their own
page and asking before it goes in the book.
</Analogy>

<TLDR>
- **Centralized** — everyone commits to a single branch. Fine for tiny teams, painful past that.
- **Feature branches** — master stays the official history; all new work happens on its own branch.
- **Pull requests** — a GitHub/Bitbucket feature (not Git) to review, discuss, approve or reject a branch.
- **Fork & clone** — every contributor gets their own GitHub copy; push to `origin`, PR to `upstream`.
- Forking and PRs are how huge open-source projects take work from thousands of strangers.
</TLDR>

<CodeBlock lang="bash" title="The feature-branch loop">{`git switch -c add-dark-theme     # branch off master
# ...add + commit...
git push origin add-dark-theme   # share the BRANCH, not master
git switch master
# master never moved, so a plain 'git merge' would just fast-forward —
# --no-ff forces the two-parent merge commit drawn above
git merge --no-ff add-dark-theme # only now does master move
git push origin master`}</CodeBlock>

<Callout type="info">
At a real company you don't just decide you're "happy with" a feature — there are
approval and merging mechanisms. That's what pull requests are for.
</Callout>

## Pull requests

> "I have this new stuff I want to merge into master... what do you all think about it?"

| Question | Answer |
| --- | --- |
| **What** | A request that one branch be merged into another |
| **Where** | Built into GitHub, Bitbucket & friends — **not** native to Git |
| **Why** | Alert teammates to work needing review; approve or reject it; discuss and give feedback |

### When a PR conflicts

<Callout type="warning">
Just like any other merge, a PR can conflict. Don't panic — fix it on the command
line as usual, or in GitHub's interactive editor.
</Callout>

<Steps
  caption="Two groups of moves: clean the branch, then move master."
  items={[
    { icon: "⬇️", label: "Fetch", note: "Get the latest origin/master without touching your work." },
    { icon: "🌿", label: "Merge master in", note: "On the feature branch, so the conflict is fixed there." },
    { icon: "🔧", label: "Fix conflicts", note: "Edit the files, strip the markers, commit." },
    { icon: "🔀", label: "Merge + push", note: "Back on master the merge is clean — push it up." }
  ]}
/>

<CodeBlock lang="bash" title="Resolving a PR conflict locally">{`git fetch origin
git switch my-new-feature   # go to the branch in question
git merge origin/master     # the freshly fetched master, not the stale local one
# fix conflicts!

git switch master
git merge origin/master     # fast-forward local master first
git merge my-new-feature    # now conflict-free
git push origin master`}</CodeBlock>

<Callout type="tip">
Forgot the steps? GitHub prints the exact command-line instructions on the PR page.
</Callout>

<CodeBlock lang="bash" title="Wiring up the two remotes">{`git clone <url-of-MY-fork>          # origin is added automatically
git remote add upstream <url-of-ORIGINAL-repo>

git push origin my-new-feature      # share via my fork
git pull upstream master            # catch up with the official repo`}</CodeBlock>

## In 30 seconds

| Workflow | Branches | Repos | Best for |
| --- | --- | --- | --- |
| **Centralized** | one, shared | 1 | Tiny teams, toy projects |
| **Feature branch + PR** | one per feature | 1 | Most company teams |
| **Fork & clone** | one per feature | 1 fork each + official | Open source, untrusted contributors |
