<Analogy>
A commit is a snapshot with a sticky note on it. `--amend` peels off the last note and re-takes the photo.
</Analogy>

<TLDR>
- `-m` = inline commit message, instead of Git launching a text editor.
- `--amend` **redoes** the previous commit — fix the message or add a forgotten file.
- Commit **early and often**, keep commits **atomic**, messages **meaningful but concise**.
- Git docs suggest **present-tense imperative** ("make xyzzy do frotz"). You don't have to — just be consistent.
- `.gitignore` in the repo root tells Git which untracked files to ignore.
</TLDR>

## The `-m` flag

No `-m`, and Git opens a text editor for the message. `-m` passes it inline.

<CodeBlock lang="bash" title="Inline message">{`git commit -m "my message"`}</CodeBlock>

## Configuring your default editor

Which editor Git launches is yours to pick.

<CodeBlock lang="bash" title="Set the commit editor">{`# --wait makes Git pause until you close the VS Code tab
git config --global core.editor "code --wait"`}</CodeBlock>

## Amending commits

Just committed and forgot a file? Typo in the message? Don't stack a second commit — redo the last one.

<CodeBlock lang="bash" title="--amend variants">{`git commit --amend                     # reuse last commit, editor opens for the message
git commit --amend --no-edit           # skip the editor, keep the old message
git commit --amend -m "fixed message"  # skip the editor, new message inline`}</CodeBlock>

<Callout type="warning">
`--amend` only touches the **most recent** commit — and since it replaces it, avoid amending anything already pushed.
</Callout>

## Writing commit messages

Present or past tense? Does it really matter?

> From the Git docs: Describe your changes in imperative mood, as if you are giving orders to the codebase to change its behavior.

| Style | Message |
| ----- | ------- |
| ✅ Imperative (docs' pick) | `make xyzzy do frotz` |
| ✅ Past tense (many devs) | `made xyzzy do frotz` |
| 🚫 Docs advise against | `[This patch] makes xyzzy do frotz` |
| 🚫 Docs advise against | `I changed xyzzy to do frotz` |

<Callout type="tip">
You do **not** have to follow the imperative pattern. All that matters is consistency — especially on a team where many people commit.
</Callout>

<CodeBlock lang="gitignore" title=".gitignore — in the repo root">{`.DS_Store
folderName/
*.log`}</CodeBlock>

| Pattern | Ignores |
| ------- | ------- |
| `.DS_Store` | Files named exactly that |
| `folderName/` | An entire directory |
| `*.log` | Any file with the `.log` extension |
