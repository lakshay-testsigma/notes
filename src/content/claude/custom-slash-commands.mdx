## Saved prompts, nothing more

Write a prompt once, save it, and Claude Code picks it up — any repeatable workflow becomes one word.

  caption="Life of a custom command."

<Callout type="warning">
**Restart requirement**: a new `.md` file only appears after you exit and restart Claude Code.
</Callout>

## When to make one

The single best signal is **repetition**.

| Command | Does | Why automate |
| --- | --- | --- |
| `/review` | Code review checklist on current file | Every time you write code |
| `/commit` | Generate a git commit message | Every feature ends with a commit |
| `/test` | Run test suite, analyse failures | Tests run after every change |
| `/security-scan` | Scan for common vulnerabilities | Security checks repeat throughout |

<Callout type="tip">If you'll type the same prompt more than twice → make it a slash command.</Callout>

## Project scope vs user scope

| Aspect | Project-scoped | User-scoped |
| --- | --- | --- |
| Location | `<project>/.claude/commands/` | `~/.claude/commands/` |
| Available | Only that one project | Every project on your machine |
| Best for | Project-specific workflows | General-purpose helpers |
| Shared via git? | Yes | No |

## Anatomy of the file

| Section | Purpose | Example |
| --- | --- | --- |
| Description | Short summary shown in dropdown | "Create a single dummy user" |
| Allowed tools | Restricts what Claude can do | `Read, Bash(python3 *)` |
| Arguments hint | (Optional) tells the user the inputs | `<user_id> <count> <months>` |
| Detailed instructions | The actual prompt, step by step | Read file X, generate Y, insert into Z |

## Example 1 — /seed-user

While building UI you need realistic users in the database to display.

<CodeBlock lang="markdown" title=".claude/commands/seed-user.md">{`---
description: Create a single dummy user in the database
allowed-tools: Read, Bash(python3 *)
---
Read database.py to understand the users table, then write and
run a Python script that generates a realistic random Indian user.

Fields: name, email, password (always "123", hashed), created_at.

Steps:
1. Check whether the generated email already exists.
2. If it does, retry until unique.
3. Insert the user using the get_db() function.
4. Print the inserted user's details.`}</CodeBlock>

<Callout type="info">
`allowed-tools: Bash(python3 *)` — Claude can only run Python via Bash; **not** `git`, `rm`, or anything else. A powerful safety boundary.
</Callout>

## Example 2 — /seed-expense with $ARGUMENTS

| Input | Meaning | Example |
| --- | --- | --- |
| `user_id` | Whose expenses are these? | 2 |
| `count` | How many expense rows | 5 |
| `months` | Spread across the last N months | 3 |

<CodeBlock lang="markdown" title="invoked as: /seed-expense 2 5 3">{`---
description: Seed realistic dummy expenses for a specific user
argument-hint: <user_id> <count> <months>
allowed-tools: Read, Bash(python3 *)
---
User input: $ARGUMENTS

Step 1 -- Extract user_id, count, months (integers).
  If any missing: show format /seed-expense <user_id> <count> <months>
Step 2 -- Verify the user exists; if not, abort with a clear error.
Step 3 -- Insert count expenses across the last months months.
  Ranges: Food 50-800 · Health 100-2000 · Travel 100-3000
          Bills 200-5000 · Shopping 100-4000 INR
Step 4 -- Print a summary of the inserted expenses.`}</CodeBlock>

<Callout type="tip">`$ARGUMENTS` receives whatever follows the command; `argument-hint` shows inline hints while you type.</Callout>

## Example 3 — /create-spec

Automates the feature spec documents you previously wrote by hand.

<CodeBlock lang="markdown" title=".claude/commands/create-spec.md">{`---
description: Create a spec file for the next Spendly feature
argument-hint: <step_number> <feature_name>
allowed-tools: Read, Write, Bash(git *)
---
You are a senior developer planning a new feature. Follow CLAUDE.md.
User input: $ARGUMENTS

Step 1 -- Parse step_number, feature_title, feature_slug.
Step 2 -- Research: CLAUDE.md, app.py, database.py, .claude/specs/.
Step 3 -- Generate a spec: Overview, Dependencies, Routes,
  Database Changes, Templates, Files Modified, New Files,
  New Dependencies, Rules, Acceptance Criteria.
Step 4 -- Save to .claude/specs/<step_number>-<feature_slug>.md
Step 5 -- Tell the user the spec has been created.`}</CodeBlock>

## Feature 1 — user registration

What the generated spec contained, in one glance:

| Area | Spec says |
| --- | --- |
| Routes | `GET /register` exists; `POST /register` new behaviour |
| Database | No schema changes; new DB helper in `db.py` |
| Templates | `register.html`: `method="post"`, action URL, error block |
| Rules | No SQLAlchemy, parameterised queries, hash passwords, server-side validation |

| # | Acceptance criterion | Result |
| --- | --- | --- |
| 1 | Visiting `/register` shows the form | Pass |
| 2 | Valid fields → user created, redirect to login | Pass |
| 3 | Mismatched passwords shows error | Pass |
| 4 | Already-registered email shows error | Pass |
| 5 | Empty fields block submission | Pass |
| 6 | Password stored as a hash, not plain text | Pass |

## Upgrading /create-spec with git guards

| Guard | Reason |
| --- | --- |
| Refuse if working tree is dirty | Prevents mixing features' WIP |
| Check branch-name collision | Two features could share a slug |
| Pull `main` before branching | New branch starts from latest state |

## Best practices

| Rule | Detail |
| --- | --- |
| Filename = command name | And restart Claude Code after creating one |
| Be very explicit | Step-by-step instructions in the file |
| Restrict with `allowed-tools` | Commands stay safe by construction |
| `$ARGUMENTS` + `argument-hint` | Flexible, parameterised commands |
| `/create-spec` first | The entry point to every new feature |
| Review specs and plans | Always, before implementation |
| Branch per feature | PR it, merge, then delete the branch |

## In 30 seconds

- A custom slash command = **a saved prompt**: Markdown in `.claude/commands/`, filename becomes `/name`, restart to discover.
- Two scopes: **project** (shared via git) vs **user** (`~/.claude/commands/`, every project).
- Four parts: description, `allowed-tools`, `argument-hint`, detailed instructions — `$ARGUMENTS` carries the inputs.
- Workflow: `/create-spec` (with git guards) → review spec → implement → test → feed gaps back.
