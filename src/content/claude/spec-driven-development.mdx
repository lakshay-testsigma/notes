<TLDR>
- **Vibe coding** = lose control to gain speed — the AI drives most decisions. **SDD** = take time upfront to gain control — **you drive every decision**.
- The **spec doc** is written before any code and acts as the **single source of truth**.
- **Agentic coding** = SDD + sub-agents + structured workflows. SDD is the foundational pillar.
</TLDR>

## Two opposite philosophies

| Approach | Philosophy | Who is in charge |
| --- | --- | --- |
| Vibe coding | Lose control to gain speed | AI drives most decisions |
| SDD | Take time upfront to gain control | You drive every decision |

## What is vibe coding?

Build software by talking to an AI in a **fast, conversational, experimental** way — no upfront plan.

## Why it breaks down — you lose control

A vague prompt forces the AI to make **dozens of crucial decisions on your behalf** — invisible until the code is already written. "Build me a user authentication system" silently answers:

| Hidden question | Why it matters |
| --- | --- |
| Which framework? | Affects every line of code that follows |
| JWT or sessions? | Different security model, different infrastructure |
| Password rules? | Affects UX + security |
| After 3 failed logins? | Lockout? CAPTCHA? Email alert? |

## What is SDD?

A detailed **specification document** is written **before any code** — it becomes the single source of truth for what the system should do. Every crucial decision is written down and handed to the AI.

| Vibe coding | SDD |
| --- | --- |
| Lose control → faster code | Keep control → slower start, but **right** code |

## Anatomy of a spec document

| # | Section | What it answers |
| --- | --- | --- |
| 1 | Problem statement | *Why* are we building this feature? |
| 2 | Functional requirements | *What* exactly will the feature do? |
| 3 | API contracts | What goes in, what comes out? |
| 4 | Constraints | Performance, screen size, limits |
| 5 | Edge cases & error handling | Where can it fail, and how do we handle it? |
| 6 | Acceptance criteria | How do we know it's "done"? |

## Full example — chat history sidebar

A ChatGPT-like app needs a **left sidebar of past conversations**. The whole spec, section by section:

<CodeBlock lang="md" title="the spec, sections 1–2">{`## Problem statement
Users create many conversations over time but have no easy
way to revisit them — hard to find, resume, and manage threads.

## Functional requirements
- Display a sidebar listing past chats
- Show a short, readable title for each chat
- Auto-generate the title from the user's first message
- Click any chat to open it`}</CodeBlock>

| Aspect | Description |
| --- | --- |
| Input | User clicks a particular past conversation |
| Output | That chat opens in the main area |

Constraints: sidebar loads **within 1 second**, works on **standard laptop screens**, titles stay **short and readable**.

| Edge case | How to handle |
| --- | --- |
| No chats yet (first-time user) | Show "No chat history yet" |
| Chat can't be loaded | Show an error message |
| First message is very long | Use only the first part as the title |

## Technical design plan — the "How" doc

The spec describes **What & Why**, non-technically (a PRD). The design plan describes **How** to build it — chat-app example:

| --- | --- | --- |
| GET | `/chats` | Fetch chat summaries (sorted by recency) |

| POST | `/chats` | Create chat (generate title + store first message) |

## Why spec and design stay separate

Mix tech details into the spec and it's tied to one stack — migrate (FastAPI → Django) and you rewrite the **entire spec**. Keep them apart and you rewrite only the plan.

| Document | Typically written by |
| --- | --- |
| Spec document | Product managers (with engineering input) |
| Technical design plan | Engineering team |

## Vibe vs SDD — head to head

| Dimension | Vibe coding | SDD |
| --- | --- | --- |
| Starting point | A feeling / rough idea | A written specification |
| Requirements | AI infers them | You define them upfront |
| Control | Low — AI leads | High — you lead |
| Speed to first result | Very fast | Slower upfront, faster overall |
| Code quality | Unpredictable | Consistent and traceable |
| Works well for | Prototypes, exploration, side projects | Production systems, teams, complex apps |
| Failure mode | Spaghetti code you don't understand | Over-specified, rigid if requirements change |

<Callout type="tip">
In SDD **you must understand programming** — you write the spec and lead the AI.
Mental model: **Claude does the typing, you do the thinking and the reviewing.**
</Callout>

## In 30 seconds

- The spec is the **single source of truth** — once it exists, no development happens outside it.
- Vibe coding fails on big features because of the **hidden decisions** the AI makes.
- Keep the **Why/What** doc separate from the **How** doc — protects against tech-stack lock-in.
